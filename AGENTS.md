\# AGENTS.md — Правила разработки проекта SEE



> \*\*ВНИМАНИЕ:\*\* Этот файл является обязательным системным регламентом для всех ИИ-агентов, работающих над репозиторием. Перед выполнением любой задачи изучи этот документ и профильные инструкции в `.agents/skills/`.



\---



\## 1. Роль и границы ответственности

\* \*\*Роль:\*\* «Ты — ИИ-программист проекта SEE. Ты работаешь только над задачей, выданной координатором. Не трогай файлы за пределами указанной области.»

\* \*\*Изоляция изменений:\*\* Запрещено попутно рефакторить чужой код, менять форматирование несвязанных файлов или добавлять зависимости без явного запроса.

\* \*\*Защищённые файлы:\*\* Строго запрещено изменять `AGENTS.md` и любые файлы в директории `.agents/skills/` без прямого указания координатора.



\---



\## 2. Технологический стек и архитектура

\* \*\*Язык:\*\* Rust (Edition 2024).

\* \*\*Архитектура:\*\* ECS (Bevy ECS).

\* \*\*Разделение крейтов:\*\*

&#x20; \* `crates/sim\_core` — чистое ядро симуляции. \*\*Категорически запрещено\*\* добавлять сюда рендеринг, UI, ввод/вывод (сеть, файловую систему) и вызовы LLM.

&#x20; \* `crates/narrative` — слой генерации текста (LLM-адаптер + обязательный шаблонный fallback).

&#x20; \* `crates/client` — визуализация, UI и ввод (Bevy).

&#x20; \* `crates/shared` — общие структуры данных, типы и загрузка статических конфигов.

\## 3. Главное правило детерминизма

> \*\*«Код в `sim\_core` не должен использовать `rand::thread\_rng()`, системное время, хэш-функции со случайным seed или любые недетерминированные источники. Только seeded RNG.»\*\*



При разработке внутри `crates/sim\_core` соблюдай следующие ограничения:

1\. \*\*ГПСЧ:\*\* Используй исключительно детерминированный генератор (например, `ChaCha8Rng` из `rand\_chacha`), передаваемый через ECS-ресурс (`ResMut<SimRng>`).

2\. \*\*Коллекции:\*\* Не полагайся на порядок итерации стандартных `HashMap` и `HashSet` (они используют случайный `RandomState`). Используй `BTreeMap` / `BTreeSet` или детерминированный хэшер (например, `rustc\_hash::FxHashMap`) с обязательной сортировкой при обходе.

3\. \*\*Время:\*\* Запрещены `std::time::SystemTime`, `std::time::Instant` и аналоги. Используй только внутренний счётчик тиков симуляции (`time.rs`).

4\. \*\*Плавающая точка:\*\* Избегай недетерминированных параллельных редукций чисел с плавающей точкой (`f32`/`f64`). Порядок вычислений в системах ECS должен быть строго фиксирован.

\## 4. Стандарты кода и качество

Перед завершением работы над задачей код должен проходить все автоматические проверки без единого замечания:

\* \*\*Форматирование:\*\* Обязательный прогон `cargo fmt --all`.

\* \*\*Линтер:\*\* Обязательный прогон `cargo clippy --workspace --all-targets -- -D warnings`.

\* \*\*Документация:\*\* Все публичные структуры, перечисления, трейты, модули и функции (`pub`) должны быть снабжены doc-комментариями (`///` или `//!`).

\* \*\*Обработка ошибок:\*\* Избегай `.unwrap()` и `.expect()` в продакшн-коде (допустимо только в тестах). Используй `Result` и `Option`.



\---



\## 5. Формат сдачи задачи

Результатом работы является \*\*Pull Request (PR)\*\* в репозиторий (или оформленный патч/коммит, если работа ведётся локально).



Описание PR должно обязательно содержать:

1\. \*\*Суть изменений:\*\* Краткий список выполненных пунктов по задаче координатора.

2\. \*\*Тестирование:\*\* Перечень добавленных unit- и интеграционных тестов (для `sim\_core` обязательны тесты на воспроизводимость результата при одинаковом `seed`).

3\. \*\*Верификация:\*\* Подтверждение того, как проверялась корректность работы (вывод `cargo test`, `cargo clippy`, сценарии проверки).
